# 真实模式技术方案（安卓端改造）

> 结论先行：**原「CDP 接管」方案对「双鱼部落」语音厅本体完全不可用。**
> 需要把"传输层"从 CDP 换成 ADB，但"业务逻辑层"（限流、去重、黑名单、送达确认思路）大部分可以保留。
> 本文档只做分析，不含代码改动。

---

## 一、为什么原方案不可用（必须先认清）

### 1.1 原方案的真实原理

读遍 `src/*.mjs` 后可以确认，原软件**不是"模拟点击界面"**，而是**直接调用客户端内部的 JS/HTTP 接口**：

| 能力 | 原实现 | 依赖 |
|---|---|---|
| 发私聊文字 | 动态 `import()` 融云模块，调 `mod[mapping.text]({targetId, content})` | **能在页面执行 JS** |
| 查 uid→rongCloudId | `window.electronAPI.piscesApi('/UI/Search/exactUser', {keyword})` | **客户端暴露的 Electron 桥** |
| 采集房间榜单 | `piscesApi('/UI/Room/UserRank/list', ...)` | **同上** |
| 自动欢迎 | `MutationObserver` 监听 DOM 新增欢迎图标 → `el.click()` | **能访问页面 DOM** |
| 语音发送 | CDP 断点取闭包 `Debugger.setBreakpointByUrl` | **CDP 调试器** |

这些**全部**建立在两个前提上：
1. 目标是 **Chromium/Electron**（有 CDP、有 `window`、有 DOM）
2. 客户端把内部能力暴露成了 **JS 接口**（`window.electronAPI.piscesApi`）

### 1.2 语音厅是安卓 App，两个前提都不满足

- 「双鱼部落」包名 `com.sybl.voiceroom`，是**安卓 APK**，跑在模拟器里
- 它不是 Chromium → **没有 CDP 端口**
- 它的内部接口是**安卓原生/网络层**，不是 `window.electronAPI` → **拿不到**
- 它没有我们熟悉的 DOM → **`MutationObserver` / `el.click()` 全部失效**

**一句话：原方案的五个模块，没有一个能直接跑在安卓上。**

## 二、目标能力拆解（用户要的三个功能）

| 功能 | 本质操作 | 安卓端等价实现 |
|---|---|---|
| **自动私聊** | 对一批目标 ID 逐个发消息 | 搜索 ID → 进会话 → 输入文字 → 点发送 |
| **自动欢迎** | 监听新用户进房 → 点欢迎 | 监听屏幕/日志中新出现的欢迎按钮 → 点击 |
| **自动打call** | 循环发表情 | 点表情按钮 |

这三个的**编排逻辑**（限流、去重、黑名单、随机延迟、今日上限、失败重试）是**与平台无关的**，可以完整保留。变的只是"怎么把消息送出去"。

---

## 三、三条技术路线深度对比

### 路线 A：ADB + uiautomator2（**推荐**）

**原理**：雷电/夜神等模拟器都开放 ADB 调试口（默认 `127.0.0.1:5555`）。
`uiautomator2` 是成熟的 Python 库，通过 ADB：
- `dump_hierarchy()` → 拿到当前界面的**完整控件树**（XML，含控件 id/text/bounds）
- `d(text="发送").click()` → **按控件语义定位后点击**（不是死坐标）
- `d.send_keys("你好")` → 输入文字
- `d.xpath(...)` → 复杂定位

**优势**：
- ✅ **按控件定位，不是坐标**——App 换版本、换分辨率都不易失效（这是它碾压图像识别的关键）
- ✅ 读取的是**安卓无障碍树**，能拿到真实的控件 ID 和文字
- ✅ 成熟的生态，稳定运行多年
- ✅ 与模拟器解耦——换成真机也能跑

**劣势 / 风险**：
- ⚠️ **依赖 App 的控件有可辨识特征**（id 或 text）。如果语音厅用的是自绘控件（游戏引擎/Flutter/Skia 画出来的），无障碍树可能是空的 → 退化到坐标点击
  - **这是最大的未知，必须先做一次"控件树探测"验证**
- ⚠️ 需要 Python 环境 + `uiautomator2` + 模拟器开启 ADB
- ⚠️ 安卓端的"送达确认"没法像 CDP 那样查 `messageUId`——只能靠**界面回显**（气泡出现）判断

### 路线 B：无障碍服务（AccessibilityService）注入

**原理**：写一个辅助 App（或 Xposed 模块）装进模拟器，用系统的无障碍权限读屏 + 操作。

**优势**：能力最强，能拿到最完整的界面语义，能监听事件
**劣势**：
- ❌ 需要**开发并签名一个安卓 App**，工作量巨大
- ❌ 需要用户手动开启无障碍权限（部分模拟器限制）
- ❌ 维护成本高，App 升级可能失效

**结论**：杀鸡用牛刀，本阶段不推荐。除非路线 A 验证失败。

### 路线 C：图像识别（Airtest / OpenCV 模板匹配）

**原理**：截图 → 模板匹配/OCR 找到按钮位置 → ADB 点击坐标。

**优势**：不依赖控件树，理论上"看得见就能点"
**劣势**：
- ❌ **脆弱**：分辨率、主题、皮肤、字体一变就失效
- ❌ 需要给每个按钮**手工截模板图**，维护地狱
- ❌ 误点风险高（语音厅界面元素密集）

**结论**：作为**路线 A 的兜底**（当控件树拿不到时的降级方案），不做主力。

## 四、推荐架构（路线 A 落地形态）

### 4.1 分层设计（关键：传输层与业务层解耦）

```
┌─────────────────────────────────────────────┐
│  task-runner（业务编排层）—— 改动很小          │
│  · 任务生命周期 / 统计 / 启停                   │
│  · 限流、去重、黑名单、随机延迟、今日上限          │
└────────────────┬────────────────────────────┘
                 │  统一驱动接口（抽象）
┌────────────────▼────────────────────────────┐
│  driver 抽象层（新增）                         │
│  定义统一动词：                                 │
│    connect() / findUser(id) / openChat(id)    │
│    sendText(s) / sendEmoji() / watchWelcome() │
│    screenshot() / dumpUi()                    │
└────────┬──────────────────────┬─────────────┘
         │                      │
┌────────▼─────────┐  ┌────────▼──────────────┐
│ CdpDriver（现有）  │  │ AdbDriver（新增）       │
│ 接管 Electron 客户端│  │ ADB + uiautomator2     │
│ 【保留给桌面场景】   │  │ 【真实模式新引擎】       │
└──────────────────┘  └───────────────────────┘
```

**核心思想**：把现在散落在 `src/*.mjs` 里的"直接调 CDP"改成"调 driver 接口"。
这样**同一个 task-runner 能同时驱动 CDP 和 ADB 两种后端**，演示模式作为第三种（MockDriver）。

### 4.2 新增组件

| 组件 | 职责 |
|---|---|
| `emulator-manager` | 检测雷电安装 → 启动模拟器 → 连 ADB → 装 APK → 拉起 App → 确认已登录 |
| `adb-driver.mjs` | 封装 uiautomator2 调用（或直接 ADB shell + 解析 XML） |
| `python-bridge` | Node ↔ Python 的进程桥（如果走 uiautomator2 Python 库） |
| **控件映射表** | 记录语音厅各关键控件的定位特征（昵称/ID/文字），**这是最需要探明的东西** |
| 设置页「模拟器连接」卡片 | 启动/连接/装APK/状态显示 |

### 4.3 三个功能的新实现思路

**自动私聊**
```
读目标 uid 列表（沿用现有 rules 逻辑）
  → 对每个 uid：
     1. 点搜索按钮 → 输入 uid → 搜索结果点第一个
     2. 进入会话页
     3. 点输入框 → 输入文案
     4. 点发送按钮
     5. 截图/读控件树 → 检测"我的气泡"是否出现（送达确认）
     6. 返回，随机延迟，下一个
```

**自动欢迎**
```
进入目标房间
  → 轮询读控件树（每 2-3 秒 dump 一次）
  → 检测新出现的"欢迎"按钮节点（对比上一帧差集）
  → 逐个点击，间隔 1.5-3 秒随机
```
> 注意：安卓端**没有 MutationObserver**，只能用"定时轮询控件树 + 前后对比"来模拟"新元素出现"。

**自动打call**
```
进入房间
  → 定位表情/礼物按钮 → 按间隔循环点击
  → 可轮换不同表情
```

## 五、必须先验证的关键未知（动手前的探测清单）

这些是"方案能否成立"的决定性因素，**必须在写代码前先用 ADB 手工验证**：

| # | 待验证 | 怎么验 | 失败后果 |
|---|---|---|---|
| 1 | **语音厅的控件树是否可读** | `adb shell uiautomator dump` 看 XML 是否有实质内容 | 若为空（自绘界面）→ 路线 A 破产，转路线 C |
| 2 | 关键控件有无稳定 id/text | dump 出来的 XML 里找"发送""搜索"等 | 无 id → 只能靠坐标，脆弱 |
| 3 | 搜索结果页能否定位到目标用户 | 手工搜索一个 ID 看结构 | 定位不到 → 私聊无法自动化 |
| 4 | 登录态能否在模拟器内保持 | 登录一次，重启 App 看是否还在 | 频繁掉登录 → 需处理验证码/风控 |
| 5 | 发送后界面是否有可靠回显 | 发一条，看气泡/时间戳 | 无回显 → 送达确认只能标记"已发出" |
| 6 | 是否有风控/检测模拟器 | 观察是否提示环境异常 | 有风控 → 需额外伪装 |

**建议：拿到环境后，第一步就做 #1（控件树探测）**，它直接决定走 A 还是 C。

## 六、可以完整保留的资产（好消息）

改造成本没有想象中大，因为**这些与平台无关，一行不用改**：

- ✅ 任务生命周期管理（`task-runner` 框架）
- ✅ 限流 / 防封逻辑：`user-resolver` 的抖动、配额、缓存思路
- ✅ 采集→发送解耦的编排
- ✅ 黑名单、今日去重、发送上限、随机延迟
- ✅ 界面（`design/`）—— 只需加一张"模拟器连接"卡片
- ✅ 演示模式（`MockDriver`）—— 完全不动
- ✅ 数据面板、统计卡片

**真正要重写的只有**：`cdp-client` → `adb-driver`，以及五个功能模块里"怎么操作界面"的那一段。业务编排骨架和界面基本不动。

---

## 七、风险与诚实的提醒

1. **最大的不确定性是控件树可读性**（见第五节 #1）。如果语音厅是自绘 UI，整条路线 A 就要换成图像识别，稳定性会明显下降。
2. **安卓端的"送达确认"天然弱于 CDP**。CDP 能拿到服务端 `messageUId` 精确确认；安卓只能看界面回显，属于"尽力确认"。
3. **模拟器 + 语音厅 + 自动化**三者叠加，资源占用不低（建议给雷电配 4 核 4G 内存）。
4. **风控**：真实发送意味着真实账号风险。原代码里的限流/抖动/配额是必要的，改造时必须保留，不能为了效率削掉。
5. **合规**：本改造仅用于技术学习；真实发送请遵守平台条款。

## 八、建议的推进顺序

```
阶段 0（环境，进行中）
  用户装雷电模拟器 → 装双鱼部落 APK → 登录账号
        ↓
阶段 1（探测，关键决策点）★ 先做这个
  用 ADB 手工 dump 控件树，验证第五节 #1~#6
  → 若可行：确定控件映射表
  → 若不可行：转图像识别路线，重新评估
        ↓
阶段 2（架构）
  引入 driver 抽象层，把 task-runner 改成面向接口
  （此时演示模式改用 MockDriver，验证抽象层没破坏现有功能）
        ↓
阶段 3（引擎）
  实现 AdbDriver：connect / dumpUi / tap / sendKeys / screenshot
  逐个实现 私聊 → 打call → 欢迎
        ↓
阶段 4（集成）
  设置页加「模拟器连接」卡片；emulator-manager 做生命周期
        ↓
阶段 5（加固）
  限流/风控/异常恢复/日志
```

## 九、一句话总结

**原方案是"CDP 直接调 JS 接口"，安卓端拿不到这个能力；新方案要换成"ADB 读控件树 + 按控件点击"。**
业务逻辑（限流/去重/编排/界面/演示模式）几乎全保留，真正重写的只有"传输层"。
**但能否走通，取决于一件必须先验证的事：语音厅的控件树是否可读。**
